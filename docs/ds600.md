# DS-600 hardware validation

Initial validation on 2026-11-14 used the user's DS-600 at `192.168.178.150`, MAC
`84:25:3f:3f:64:23`, firmware **1.4.4** (UDP transport version **2.3.0**).
Host: Ubuntu **26.04.1**, x86-64, kernel **7.0.0-38-generic**.

The same unit was subsequently upgraded to **1.5.0** and given a persistent
32-interface startup setting. After a further reboot with SSH disabled, all
six USB devices attached to the Linux system, including the Logi Bolt keyboard
receiver: 18 interfaces in total. Both Dell monitors were restored to
2560×1440 at 60 Hz, and the owner confirmed both screens, keyboard, mouse and
audio work. The previously patched EVDI module remained loaded. The detailed
storage, audio and Bluetooth benchmarks below were run on 1.4.4; they were not
all repeated on 1.5.0. See [firmware changes](ds600-firmware.md) and
[recovery instructions](ds600-recovery.md).

This is a userspace bridge into Linux's existing `vhci-hcd`, `usb-storage` and
`btusb` drivers. No custom kernel module or server firmware update is required.
The implementation extends the MIT-licensed OpenSilexLink project from upstream
commit `7198e0ead83f6d1ae6095d64c1945a671579a464`.

driver and EVDI are installed separately from OpenSilexLink using the
[official Synaptics repository](https://www.synaptics.com/products/displaylink-graphics/downloads/ubuntu).
EVDI DKMS modules built for both installed generic kernels, 7.0.0-38 and
7.0.0-43. No host reboot was needed.

The dock's auxiliary Cypress Billboard device (17ef:a35f) initially enumerated,
then vanished from the DS-600's own device list. It is not counted as a working
attachment. The dock's video, network and receiver devices remained attached.
Ethernet throughput still requires validation.

## Audio transport and composite-device recovery

Enabling PipeWire initially exposed two isochronous transport defects: the
DS-600 audio header contained a legacy frame counter where the firmware expects
the endpoint's bInterval, and a FIFO audio reader blocked cancellation at
stream stop. The resulting reset disconnected the whole composite DisplayLink
device, blanking both screens while the connection manager itself stayed alive.

DS-600 audio now uses the descriptor interval and a concurrent sender/receiver
with sequence-based cancellation. Endpoint parameters are cached from the
configuration descriptor instead of queried on an active audio connection.
Regression tests cover both directions' timing fields, cancellation of a
pending capture, starting another capture, and waking the USB/IP reader on a
real tunnel EOF.

Hardware checks passed at 48 kHz/S16_LE: five-second stereo playback with
simultaneous stereo capture, followed by six-channel playback with simultaneous
stereo capture. Each cycle included four seconds idle after stopping, beyond
the previous three-second failure point. The USB device number and DisplayLink
process ID stayed unchanged. PipeWire playback also completed, and its stereo
capture returned exactly 240,000 frames (960,000 bytes) in about five seconds.
These checks establish transport operation and clean stops, not long-term
dropout performance or a listening assessment. No persistent audio-disable
rule is installed on the test host.

The current CSR8510 A10 adapter (0a12:0001) pairs and connects the owner's
MOMENTUM 3. PipeWire and WirePlumber must be running for BlueZ to register A2DP
endpoints; otherwise pairing succeeds but connection fails with `Protocol not
available`. The developer user's audio services are enabled, and aptX playback
completed successfully through the DS-600.
Hands-free mode was also exercised: `hcitool con` showed an active eSCO link,
PipeWire reported running mSBC capture, and ten seconds at 16 kHz/mono/S16_LE
returned 160,000 frames (320,000 bytes) with a simultaneous playback test.
Stopping capture left the dock attached and the DisplayLink process unchanged.
The original aptX playback profile was restored afterward.

The system-service bind-all policy was exercised through the installed GUI:
all four available dock devices remained connected when the policy was turned
off, and turning it on restored automatic binding. An unexpected kernel detach
of the unused Ethernet interface recovered automatically. A deliberate IPC
Disconnect remained disconnected through a discovery cycle, then explicit
Connect restored it. These checks ran with the GUI closed during recovery.

The logged-in GNOME/Wayland session initially produced EVDI `Failed to map
scanout buffer` errors, a black display with a working cursor, and cursor lag
while the framebuffer was static. A separately packaged EVDI 1.15.1+osl1
workaround adds PRIME mapping callbacks and keeps importer mappings separate
from the painter's mapping. OpenSilexLink also enables TCP_NODELAY on incoming
USB/IP connections to avoid delaying small messages during idle video.
After reloading EVDI and restarting the graphical session, the mapping errors
stopped. The owner confirmed both screens and smooth cursor movement with
video paused. No host reboot was required. See [DisplayLink](displaylink.md)
for patch provenance, build and rollback instructions. These changes were
validated together; their individual effect on cursor latency was not isolated.

The SanDisk serial is `AA010906141526171028`. It contains a Proxmox hybrid
installer ISO named `PVE`. The stable device path is:

```
/dev/disk/by-id/usb-SanDisk_Extreme_AA010906141526171028-0:0
```

On this test host it was mounted read-only at `/mnt/silex-ds600`, before the
owner replaced the attached devices with the dock. A systemd mount
unit starts the connection manager and unmounts before that service stops. This
host-specific unit is not shipped in the package. For a manual mount:

```sh
sudo mkdir -p /mnt/silex-ds600
sudo mount -t iso9660 -o ro /dev/disk/by-id/usb-SanDisk_Extreme_AA010906141526171028-0:0 /mnt/silex-ds600
```

The first 64 MiB read twice after dropping that range from page cache yielded
SHA256 `e985ca5ce4ec6d4b1a8c04600c3df6410bc730ce3d078a0a9957df0594a58952`.
No disk formatting or data writes were performed.

Bluetooth controller address: `00:16:A4:D1:EF:36`. BlueZ discovery starts and
reports nearby advertisements through the DS-600. Pairing, sustained ACL traffic,
Bluetooth audio/SCO and isochronous transfers still require hardware validation.
Discovery establishes that the dongle works beyond descriptor enumeration;
it does not establish every Bluetooth profile.

## Device configuration

The owner factory-reset the device. Its web administrator password was set and
login verified at the owner's request; credentials are not stored in this repo.
The DS-600 NAS service initially owned the SanDisk, hiding it from USB device
server discovery. NAS was disabled through the authenticated web interface and
the unit restarted. Both USB devices then appeared in discovery.

Web settings: `http://192.168.178.150/`. The administrator password and per-port
USB connection passwords are independent. This test uses no per-port password.
To reset a lost administrator password, follow the vendor's DS-600 setup guide:
power off, hold the recessed reset button while powering on, release after the
orange LINK indication (about six seconds). This clears network and other
settings too; rediscover its IP afterwards.

## Protocol changes validated on this unit

- Parse DS-600 `usbB-DDD:I` IDs, device flags, interface grouping and speed tags.
- Complete UDP query/commit on the same socket, acknowledging the actual reply
  length, including DENY replies. Retry a refused TCP connect while the reserved
  listener starts.
- Encode DS-600 request headers and decode its shorter response headers.
- Join segmented bulk responses: status 2 means continuation, not a USB error.
  This was essential for storage reads.
- Forward USB/IP UNLINK as a cancellation with the original Silex sequence and
  endpoint. Without this, abandoned interrupt requests consumed later HCI
  completions and Bluetooth discovery timed out.

Vendor Windows client binaries and an extracted firmware image were inspected
outside the repository to understand framing and cancellation. Firmware routines
were also emulated to validate USB-password encoding test vectors. No vendor
binary or firmware is incorporated into the public release. The test unit was
subsequently updated and patched as described in [firmware notes](ds600-firmware.md).
The public Linux SX Virtual Link SDK is distributed through a vendor
contact/custom-build process; no SDK request was submitted.

See [operations](operations.md) for installation, access, startup and limitations,
and [protocol](protocol.md) for the packet layout.
